Grundlage: kritische Prüfung von mathechecks-schema-final.md sowie

----------------------------------------------------------------
1. BEFUND IST-ZUSTAND (Grundlagen fehlen – wichtiger als Schema)
----------------------------------------------------------------

1.1  jekyll-seo-tag deklariert, aber wirkungslos
     - Plugin steht in _config.yml, aber {% seo %} wird in
       _includes/head.html nie eingebunden.
     - Folge: keine Canonical-URL, keine Open-Graph-/Twitter-Tags,
       kein og:image auf der gesamten Site.

1.2  Kein sitemap.xml, kein robots.txt
     - jekyll-sitemap fehlt komplett.
     - Ohne Sitemap entdeckt Google die ~100+ Modulseiten nur über
       interne Links – und die sind teils nicht crawlbar (1.4).

1.3  Eigentlicher Content ist für Crawler unsichtbar
     - recall-content.html u. a. sind leere <div>-Container; alles
       wird client-seitig aus checks.json gerendert.
     - Google rendert JS verzögert/unzuverlässig; AI-Crawler
       (GPTBot, ClaudeBot, PerplexityBot) führen KEIN JS aus.
     - Für GEO der kritischste Punkt: Trainings-/Recall-/Flashcard-
       Seiten sind aus AI-Sicht faktisch leer.

1.4  Navigation nicht crawlbar
     - <select>-Dropdown mit <option value> ist für Crawler kein
       Link. Es braucht echte <a href>-Pfade zu allen Lernbereichen
       (Übersichtsseiten, Footer, material.html prüfen).

1.5  Titles/Descriptions schwach
     - "Binomialverteilung - Recall – MatheChecks" bzw.
       "Lernbereich Binomialverteilung, Modul Recall." matcht keine
       Suchintention. Gesucht wird: "Binomialverteilung Aufgaben",
       "Bernoulli-Formel erklärt", "Binomialverteilung Abitur".

1.6  Performance / Core Web Vitals
     - Jede Modulseite lädt Plotly (~3,5 MB), math.js, jQuery,
       Select2, Font Awesome, MathJax, Google Fonts – großteils
       blocking von CDNs. Kostet Ranking und Rendering-Budget.

1.7  Überschriftenstruktur defekt (verifiziert)
     - topbar.html rendert <h1>MatheChecks</h1> auf JEDER Seite.
     - start-content.html hat zusätzlich eine fachliche <h1>
       → doppelte h1 auf Startseiten.
     - Alle anderen Modulseiten haben nur die Marken-h1, keine
       fachliche Hauptüberschrift im statischen HTML.
     - Fix: Topbar-Logo auf <div>/<span> umstellen, jede Seite
       bekommt genau eine fachliche h1.

2. KRITIK AM SCHEMA-KONZEPT (mathechecks-schema-final.md)
----------------------------------------------------------------

2.1  Gut / beibehalten
     - jsonify statt {{ }}-Interpolation (LaTeX-Backslashes!).
     - Prinzip "sichtbarer Content parallel zum Markup"
       (module-intro.html). Google ignoriert/bestraft Markup ohne
       sichtbare Deckung. Die Recall-<ul> mit echten Kompetenz-
       formulierungen ist der wertvollste Teil des Plans.
     - Kompetenzen aus checks.json statt Doppelpflege.

2.2  Interne Widersprüche
     - Dokument verkündet "eine einzige Quelle"
       (_data/lernbereiche/<slug>.yml), referenziert aber weiterhin
       site.data.lernbereiche_liste in schema-course.html und
       module-intro.html.
     - Geplanter Ordner _data/lernbereiche/ kollidiert mit der
       existierenden flachen Datei _data/lernbereiche.yml – beide
       hießen site.data.lernbereiche. Vor Rollout entscheiden.

2.3  Course als Dach-Entity fragwürdig priorisiert
     - Google zeigt Course-Rich-Results nur mit hasCourseInstance/
       offers. Ohne diese: kein Snippet-Gewinn, Markup wirkt "nur"
       als Entity-Signal (für GEO okay, aber Erwartung anpassen).
     - Für Skript-Seiten wären LearningResource + ggf. Article/
       FAQPage teils wirksamer.

2.4  Duplicate-Content-Risiko
     - Identisches Course-Markup + identische Description
       (Fallback lb.worum_geht_es) auf 7 Seiten pro Lernbereich
       erzeugt Near-Duplicate-Signale.

2.5  Strategische Frage fehlt: Was soll überhaupt indexiert werden?
     - Recall, Flashcards, Training sind App-Seiten ohne
       Standalone-Content. 7 dünne Seiten pro Lernbereich
       verwässern eher.
     - Vorschlag: Indexierungskraft auf start + skript
       konzentrieren; App-Seiten per Canonical auf die
       Lernbereich-Startseite zeigen lassen oder bewusst schlank.

2.6  Technischer Bruchpunkt
     - where/sort auf site.data.<ordner> (Hash) funktioniert in
       Jekyll nicht zuverlässig. Kein Detail, sondern
       wahrscheinlicher Bruchpunkt – vor Rollout testen bzw.
       Array-Umwandlung fest einplanen.
     - Zudem: _data/lernbereiche.yml hat mehrere bestehende
       Verbraucher (Topbar, Dashboard, Materialseite,
       Start-Include), die ein Array erwarten. Die Umstellung auf
       _data/lernbereiche/<slug>.yml ist eine echte Migration,
       keine lokal begrenzte SEO-Anpassung – daher vom ersten
       SEO-Rollout entkoppeln.

2.7  Semantikfehler im Entwurf: assesses / syllabusSections
     - Der Entwurf verknüpft Module per
       assesses → { "@id": "...kompetenzliste.html#syllabus" }.
       Schema.org erwartet bei assesses aber eine Kompetenz
       (DefinedTerm oder Text), keinen ganzen Lehrplan.
     - syllabusSections ist eine Course-Eigenschaft und erwartet
       Syllabus-Objekte; eine DefinedTerm-Liste gehört dort nicht
       hinein.
     - Besseres Modell:
       * jede Kompetenz = DefinedTerm mit stabiler @id aus check_id
       * Course → teaches → DefinedTerms
       * Training/Recall/Feynman/Flashcards → assesses → genau die
         Kompetenzen, die sie tatsächlich prüfen
       * Course.hasPart → konkrete Lernressourcen
       * WebPage beschreibt die URL, mainEntity den Inhalt

2.8  Quiz-Typ nur bei echtem, sichtbarem Quiz
     - Recall nicht allein wegen des Namens als Quiz markieren;
       Markup muss sichtbaren Fragen/Antworten entsprechen.
     - Googles Education-Q&A-Rich-Result (inkl. eduQuestionType
       "Flashcard") ist lt. Doku nicht für Deutsch verfügbar –
       kein Snippet-Gewinn einplanen. Semantisches Markup kann
       trotzdem sinnvoll sein (GEO/Entity-Signal).
     - Generell: weniger, vollständiges, korrektes Markup schlägt
       viele ungenaue Eigenschaften.

3. WAS NOCH FEHLT (über SEO + Schema hinaus)
----------------------------------------------------------------

3.1  GEO (Generative Engine Optimization)
     - Bing Webmaster Tools einrichten: Bing-Index speist
       ChatGPT Search und Copilot.
     - AI-Crawler in robots.txt explizit ERLAUBEN
       (GPTBot, ClaudeBot, PerplexityBot, Google-Extended je nach
       Präferenz).
     - Kern für GEO ist plattformunabhängig: statisch zugänglicher
       Text, direkte fachlich eindeutige Antworten, kurze
       Definitionen neben Herleitungen, stabile URLs und Anker,
       zitierbare Abschnitte ohne Client-Interaktion, Konsistenz
       zwischen sichtbarem Inhalt und JSON-LD.
     - llms.txt: optionales Experiment mit geringem Aufwand, aber
       kein etablierter Standard – niedrige Priorität, kein Ersatz
       für robots.txt/Sitemap/sichtbaren Inhalt.

3.2  E-E-A-T
     - Autorenprofil (Dr. Sven Führing) sichtbar verlinken,
       Person-/Organization-Schema mit sameAs.
     - Bei Bildungsinhalten gewichtet Google Autorenschaft.
     - konzept.md / ueber-mich.md sind gute Grundlagen dafür.
     - Zusätzlich: Aussagen wie "gut belegte Erkenntnisse der
       Lernpsychologie" (konzept.md) mit Quellen/kurzer
       Literaturbasis stützen; redaktionelle/fachliche Grundsätze
       und Prüf-/Aktualisierungsdatum sichtbar machen; Grenzen der
       KI-Bewertung transparent beschreiben.

3.3  Off-Page (größter Hebel überhaupt)
     - Backlinks von Lehrerportalen (ZUM, Lehrerforen,
       Schul-Linklisten, Fachschaftsseiten).
     - Ohne Links rankt auch perfektes Markup nicht.

3.4  Messung
     - Google Search Console + Bing Webmaster Tools ZUERST
       einrichten – sonst blinde Optimierung.

4. PRIORITÄTEN-EMPFEHLUNG
----------------------------------------------------------------

Leitprinzip: vertikaler Pilot statt Big Bang. Erst EIN Lernbereich
(z. B. Binomialverteilung) komplett sauber (indexierbar, Kern im
HTML, Titles/h1, kleines korrektes Schema), messen, dann Muster auf
weitere Lernbereiche übertragen. Änderungen zeitlich staffeln,
damit ihre Wirkung unterscheidbar bleibt.

P0  Messbasis & Inventar (vor allen Änderungen)
    - Google Search Console + Bing Webmaster Tools einrichten/
      verifizieren.
    - Ist-Stand sichern: indexierte URLs, Impressionen,
      Suchanfragen, Landingpages.
    - URL-Inventar nach Seitentyp; Indexierungsentscheidung pro
      Seitentyp dokumentieren.

P1  Fundament (geringer Aufwand, sofortige Wirkung)
    - {% seo %} in head.html einbinden (Canonical, OG, Title)
    - jekyll-sitemap aktivieren (nur kanonische, indexierbare URLs)
    - robots.txt anlegen (Sitemap-Verweis, AI-Crawler-Freigabe)
    - h1-Struktur fixen (1.7): Topbar-Marken-h1 ersetzen,
      fachliche h1 pro Seite
    - www-/https-Variante, Statuscodes, Weiterleitungen prüfen

P2  Indexierungsstrategie entscheiden
    - Vorschlag: start + skript als primäre Landingpages;
      kompetenzliste ggf. zusätzlich (klare Lernziele = echter
      Standalone-Wert).
    - Training/Recall/Feynman/Flashcards nur indexieren, wenn ihre
      Kerninhalte statisch sichtbar und eigenständig sind – sonst
      canonical auf die Lernbereich-Startseite oder noindex.
    - Konto, Feed, Dashboard: noindex.
    - Entscheidung anhand echter Inhalte + Search-Console-Daten,
      nicht pauschal.

P3  Sichtbarer Content + Meta-Texte (Progressive Enhancement)
    - Zielregel: Jekyll liefert den fachlichen Kern als HTML;
      JS ergänzt Interaktion, Bewertung, Personalisierung.
    - module-intro-Ansatz umsetzen, aber über Standardsätze
      hinaus: jede indexierbare Seite beantwortet konkrete
      Nutzerfragen (Definitionen, Formeln, typische Fehler),
      sinnvoll auf Module verteilt statt überall wiederholt.
    - Einzigartige, suchintentions-orientierte Titles und
      Descriptions pro Seite.
    - Crawlbare <a>-Links: Gebiet > Lernbereich > Modul,
      Voraussetzungen/verwandte Themen als normale Links.

P4  Schema Markup (klein, korrekt, bereinigt)
    - Site-Ebene: WebSite, Organization, Person (Autor),
      BreadcrumbList.
    - Lernbereich: Course mit about, educationalLevel, provider,
      author, isAccessibleForFree, teaches (DefinedTerms),
      hasPart (nur indexierte Module), coursePrerequisites.
    - Seitenebene: WebPage + passende mainEntity (Article nur bei
      artikelartigem Skript, LearningResource sonst, Quiz nur bei
      sichtbarem Q&A), assesses auf konkrete DefinedTerms (2.7).
    - Widersprüche aus 2.2 auflösen, Duplicate-Risiko aus 2.4
      entschärfen. Kein Rich-Result-Gewinn einplanen (2.3, 2.8).

P5  Datenkonsolidierung (eigene Migration, nach dem Piloten)
    - Eine kanonische Quelle pro Lernbereich; Namenskollision
      _data/lernbereiche/ vs. lernbereiche.yml auflösen; alle
      Verbraucher (2.6) gemeinsam umstellen.
    - checks.json: _data/checks.json als Build-Quelle,
      /checks.json daraus generieren (Front-Matter + jsonify) –
      HTML, JSON-LD und Client nutzen dieselben Daten.
    - Build-Prüfungen: fehlende Referenzen, doppelte IDs,
      ungültiges JSON-LD.

P6  Performance (parallel, mittelfristig)
    - Plotly/math.js/Select2 nur laden, wo tatsächlich benötigt
      (pro Seitentyp/Bedarf statt global im Layout).
    - CDN-Abhängigkeiten reduzieren, Fonts self-hosten.
    - Feste Dimensionen für Bilder/Widgets gegen Layout-Shifts.
    - Messen mit PageSpeed Insights / Felddaten.

Off-Page (kontinuierlich, größter externer Hebel)
    - Backlinks von Lehrerportalen, Schul-Linklisten,
      Fachschaftsseiten aufbauen – ohne Links rankt auch
      perfektes Markup nicht. (Fehlt in der Zweitanalyse komplett.)

----------------------------------------------------------------

Messgrößen:
- gültig indexierte kanonische URLs

- organische Einstiege → anschließende Lerninteraktion
